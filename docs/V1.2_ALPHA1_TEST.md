# Firewall Local — V1.2 alpha1 TCP/IPv4

## Scope

This alpha turns the validated V1.1 diagnostic path into a real TCP/IPv4 proxy:

`TUN -> IPv4/TCP parser -> UID -> protected SocketChannel -> remote TCP`

and back:

`remote TCP -> SocketChannel -> TCP packet builder -> TUN`

Not included: UDP, DNS relay, IPv6 forwarding, TCP out-of-order reassembly, or per-app allow/block rules.

## Important Android architecture

The TUN reader is a dedicated blocking thread. It feeds a queue consumed by a single NIO Selector thread. The selector thread owns all TCP sockets and TCP session state.

For each new client SYN, the destination socket is created, protected with `VpnService.protect()` before `connect()`, switched to non-blocking mode, and connected. Only after the real destination connection is established does the engine send the synthetic SYN/ACK to the client side of the TUN.

## First device test

Do not start with normal web browsing by hostname. DNS is intentionally not implemented in this alpha.

On a PC connected to the same LAN as the Android device:

```text
python -m http.server 8080 --bind 0.0.0.0
```

Find the PC's LAN IPv4 address and browse from Android to:

```text
http://PC_LAN_IP:8080
```

This tests TCP without depending on DNS.

Windows Firewall may ask for permission for Python. Allow it on the private network used for the test.

## Expected log

A successful flow should contain events similar to:

```text
TCP SYN ...
TCP OPEN ...
TCP CONNECTING ...
TCP REMOTE_CONNECTED + SYN_ACK_SENT ...
TCP ESTABLISHED ...
TCP C2S_DATA ...
TCP S2C_DATA ...
TCP CLOSED ...
```

The exact ordering of `CONNECTING` versus `REMOTE_CONNECTED` depends on whether the non-blocking connect completes immediately.

## Host-side validation already performed

A standalone JVM harness was run against the same forwarding engine logic with a local TCP server. It verified:

- SYN -> SYN/ACK generation with a non-zero proxy ISN.
- Correct client ACK handling.
- Client-to-server payload forwarding.
- Server-to-client payload packet generation.
- TCP/IP checksum validity on generated packets.
- TCP 32-bit sequence-number wrap helpers.
- RST/ACK generation when the destination connect fails.

These tests do not replace the Android-device test: the real VPN/TUN and `VpnService.protect()` behavior still have to be validated on the handset.

## Alpha limitations

1. Only IPv4/TCP is forwarded.
2. UDP and DNS are dropped by design.
3. IPv6 is reported as unsupported.
4. Fragmented IPv4 packets are reported and not forwarded.
5. Client out-of-order TCP data is not buffered; the engine ACKs the last contiguous sequence and relies on retransmission.
6. The engine is an experimental proxy, not production-grade TCP implementation yet.
